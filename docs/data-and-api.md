# Данные и API

Какие данные хранит chronicle, откуда они берутся и как их получить. Зачем сервис и почему он устроен именно так — в [spec.md](spec.md); что обязан делать адаптер агента и формат отчёта — в [agent-contract.md](agent-contract.md).

Пометка **v2** — модель работы v2 (этап 6 [плана](plan.md)): описана, но ещё не реализована. Всё без пометки работает сейчас.

## 1. Поток данных

```text
Запись (только через локальный CLI — у него есть outbox):

  агент ──/finish, хук завершения──▶ chronicle finish ──▶ outbox ──▶ POST /v1/reports ──▶ SQLite
            (адаптер агента)          лог сессии → активность, ходы    (очередь на диске,           │
                                      выжимка дешёвой моделью агента    уходит при связи)            ▼
                                      коммиты из git                                         курирование знаний
                                                                                             (фон, LLM сервиса)
Чтение:

  CLI  chronicle search / show ──▶ GET /v1/knowledge/…      ◀── знания
  MCP  knowledge_search / get  ──▶ /mcp                     ◀── знания
  CLI  chronicle report day    ──▶ GET /v1/facts  (v2)      ◀── факты работы → проекции
  внешние отчёты               ──▶ GET /v1/facts  (v2)
```

Два контура данных:
- **работа** — факты сессий: активность, ходы, результаты, коммиты. Хранятся как есть и не меняются; эпизоды, время и метрики вычисляются при чтении;
- **знания** — ловушки и неочевидные факты окружения. Агент присылает кандидатов, сервис сам сливает их в курированную базу.

## 2. Объектная модель

```text
Справочники:  Person (v2)   Project ─< ProjectRemote      (Customer — задел)

Факты (хранятся, неизменны):
  Session ─< Segment ─< ActivityEvent   at, actor
                     ─< Turn (v2)       idx, at, project, focus
                     ─< Outcome         project, focus, text      (сейчас — WorkItem: text)
                     ─< Commit          project, hash, subject, at
                     ─< SegmentFile     project, path
                     ─< KnowledgeCandidate → KnowledgeEntry (курирование)
                                                 └─< KnowledgeUsage, KnowledgeHistory

Проекции (вычисляются при чтении):
  Episode · TimeEntry (человек × проект × день) · Metrics · Report
```

### Person (v2)
- `id` — slug (`nur`); каждый токен клиента в настройках сервиса сопоставлен человеку;
- сессия получает `person` по токену, с которым пришёл отчёт. `host` остаётся атрибутом источника;
- сессии, принятые до появления людей, при запуске сервиса отдаются человеку, если в настройках он один.

### Project
- `id` — slug (`u7-school`);
- `remotes[]` — нормализованные remote (`git@github.com:x/y.git` → `github.com/x/y`; SSH-алиас хоста раскрывается в настоящий хост);
- если remote нет — идентификация по `host + path`;
- неизвестный проект создаётся при первом отчёте;
- проектом считается только git-репозиторий: пути вне git (`~/.pi/agent`, `/tmp`) проекта не образуют (v2; сейчас проектом становится каталог запуска).

### Customer (задел)
Не вводится. Если понадобится — либо `customer` у проекта, либо отчётность целиком во внешнем сервисе поверх `GET /v1/facts`. Модель фактов от этого не меняется.

### Session и Segment (транспорт)
- **Session** — `(agent, agentSessionId)`, уникальна; хранит `host`, `cwd`, `person` и `launchProject` (справочно, для метрики «работа вне проекта запуска»); проект работы — у хода.
- **Segment** — единица приёма: один `/finish`. Продолженная сессия присылает следующий сегмент с дельтой. Ключ идемпотентности — `(agent, agentSessionId, seq)`: повторная отправка того же сегмента ничего не меняет.
- `summary` сегмента — одна фраза о результате, для ленты.
- v2: сегмент может быть помечен `superseded` — его факты работы заменены пересборкой сессии (§3 «Пересборка»); кандидаты знаний остаются.

### ActivityEvent
- `{ at, actor: 'user' | 'agent' }` внутри сегмента;
- `activitySource` сегмента: `log` (точные метки из лога) или `coarse` (известен только интервал — например, данные, перенесённые из pi-chronicle).

### Turn (ход, v2)
- `idx` — номер хода в сессии (сквозной по сегментам), `at` — время реплики человека.
- Ход длится от своей реплики до реплики следующего хода (или конца сегмента); события активности относятся к ходу по времени.
- `project` определяет адаптер по путям в вызовах инструментов хода: путь → git-корень → проект. Веса: правка файла (Edit/Write) — 3, `cd`/git-команда в shell — 2, чтение и поиск — 1; побеждает наибольший вес. Ход без путей наследует проект предыдущего, первый ход — `launchProject`. Если проекта нет ни у одного хода и запуск вне git — `project = null`.
- `focus` — короткая метка части работы (≤ 60 символов, свободный текст) от модели при выжимке: модель размечает эпизоды диапазонами номеров ходов (см. `agent-contract.md`). Для устойчивости меток в промпт подаются недавние фокусы затронутых проектов с просьбой переиспользовать подходящие.
- Сегмент без ходов (старые данные, `coarse`) читается как один ход: весь интервал → проект сессии, фокус пуст.

### Outcome (что сделано)
- `{ project, focus, text }` — конкретный результат эпизода: что реализовано, исправлено, решено. Язык результата, а не действий.
- Доказательства — коммиты и файлы того же проекта за интервал эпизода.
- Сейчас — `WorkItem { text }` без проекта и фокуса: список результатов сегмента.

### Commit и SegmentFile
- Коммиты автора (по `user.email` репо) за интервал сегмента: `{ project, hash, subject, at }`. Сейчас — только из репо каталога запуска; v2 — **из всех репозиториев, затронутых ходами сегмента**. Один коммит, пришедший из двух параллельных сессий, в проекциях учитывается один раз (`project + hash`).
- Изменённые файлы — пути относительно корня своего репо (v2 — с проектом).

### Episode (проекция, v2)
- Подряд идущие ходы человека с одинаковыми `(project, focus)` — **по всем его сессиям**, в порядке времени.
- Пауза больше порога простоя внутри эпизода — простой (не входит в активное время), но не граница.
- Возврат к тому же фокусу после другого — новый эпизод («возврат», `spec.md` §4).
- Эпизод не переходит границу дня (локальная дата человека).

### Время (проекция)
- **Активные интервалы** сегмента: промежутки между соседними событиями не длиннее `idleGapMinutes`; для `coarse` — весь интервал. Порог — параметр чтения.
- Интервал относится к проекту хода, в котором лежит.
- **Время человека** за период = длина объединения всех его активных интервалов по всем сессиям.
- **Время по проекту** = длина объединения интервалов этого проекта.
- **Параллельное время** = длина участков, где одновременно активны две и более сессии. Показывается как есть: `5.6 ч (паралл. 1.1 ч)`; сумма по проектам может превышать время человека ровно на параллельные участки разных проектов.
- `actor` событий сохраняется: время агента без участия человека можно выделить позже, не меняя данные.

### KnowledgeCandidate (вход, неизменяемый)
- `scope`: `project` | `global`; проект кандидата со scope `project` — основной проект сегмента (больше всего ходов, при равенстве — проект запуска);
- `kind`: `trap` (ловушка: симптом → причина → решение) | `fact` (неочевидный факт окружения: пути, серверы, ограничения);
- `title`, `symptoms[]` (дословные тексты ошибок — главный ключ поиска), `cause`, `fix`, `tags[]`;
- статус курирования: `pending` → `created` | `merged` | `discarded` + причина решения, ссылка на запись.

### KnowledgeEntry (курированная запись)
- `id`, `scope` (`global` или проект), `kind`, `title`, `symptoms[]`, `cause`, `fix`, `tags[]`;
- `history[]` — `{ at, candidateId, action, note }` (`created`, `merged`, `imported`, `archived`…);
- `status`: `active` | `archived` (архивная запись не ищется, но не удаляется);
- статистика: `found` (сколько раз попала в выдачу), `opened`, `lastUsedAt`; «помогло / не помогло» — из Usage.

### KnowledgeUsage
- `{ entryId, segment?, helped: true | false | null, at }` — приходит в отчёте сегмента (основной путь, из выжимки) или отдельным вызовом.

## 3. Процессы над данными

### Приём отчёта (синхронно)
Валидация по контракту → запись сегмента, активности, ходов, результатов, коммитов, файлов, кандидатов и usage одной транзакцией → `202` с ID. Неизвестные проекты создаются. Курирование не блокирует приём. Принимаются контракты v1 (накопленный outbox; читается как сегмент без ходов) и v2.

### Пересборка сессии (v2)
`chronicle replay --agent <a> --session <id>`: адаптер перечитывает лог сессии целиком, выжимка — без знаний (`knowledge: []`, `usage: []`, чтобы не плодить дубли кандидатов), отчёт уходит с флагом `replace`. Сервис одной транзакцией помечает прежние сегменты сессии `superseded` (их ходы, результаты, коммиты, файлы и активность из проекций исключаются; кандидаты знаний остаются) и пишет новый сегмент. Используется при смене модели разметки и для исправления ошибок.

### Курирование знаний (асинхронно, в сервисе)
Для каждого кандидата `pending`:
1. нечёткий поиск топ-5 похожих записей в своём scope и в общем;
2. LLM решает: `create`, `merge <id>` (с обновлёнными полями) или `discard` (тривиально, общеизвестно или полный дубль);
3. решение применяется и логируется в `history` записи и в кандидате.

Запускается сигналом после каждого отчёта с кандидатами и по таймеру (`curateIntervalSeconds`). Курирование можно перезапустить по всем кандидатам (пересборка базы).

### Архивирование
Записи без использования дольше `archiveAfterDays` переводятся в `archived`.

## 4. Хранилище (SQLite)

Один файл БД (`dbPath`), схема версионируется миграциями (`src/infra/migrations.ts`, таблица `schema_migrations`).

| Таблица | Что хранит |
|---|---|
| `projects` | проект: `id` (slug), `name` |
| `project_remotes` | нормализованный remote → проект |
| `project_paths` | `(host, path)` → проект — для репо без remote |
| `sessions` | `(agent, agent_session_id)` уникально; `host`, `cwd`, `person`, `launch_project` (NULL — запуск вне git) |
| `segments` | `(session_id, seq)` уникально; интервал, `activity_source`, `summary`, `received_at`, `superseded` |
| `activity_events` | `at`, `actor` по сегменту |
| `outcomes` | результаты сегмента: `project_id`, `focus`, `text` |
| `turns` | ходы: `idx`, `at`, `project_id`, `focus` |
| `commits` | `project_id`, `hash`, `subject`, `at` по сегменту |
| `segment_files` | `project_id`, путь изменённого файла |
| `persons` | люди |
| `knowledge_candidates` | кандидаты из отчётов, `project_id` (основной проект сегмента), статус курирования, решение, число попыток и последняя ошибка |
| `knowledge_entries` | курированные записи и счётчики `found`, `opened`, `last_used_at` |
| `knowledge_history` | история записи |
| `knowledge_usage` | отметки пользы |

Массивы (`symptoms`, `tags`) хранятся JSON-строкой. Переход на v2 — миграцией без конвертации старых данных: `project_id = NULL` у результатов, коммитов, файлов и кандидатов читается как проект запуска сессии, старые сегменты — по правилу «сегмент без ходов»; живые сессии пересобираются через `replay`. Бэкап — копия файла (`sqlite3 .backup`).

## 5. HTTP API

JSON. Все пути, кроме `/v1/health`, требуют `Authorization: Bearer <токен>`; без него — `401`.

### Отчёты

**`POST /v1/reports`** — приём сегмента. Тело — `SessionReport` (v1: `contract/v1.ts`; v2: [agent-contract.md](agent-contract.md#sessionreport-v2-что-уходит-в-сервис)). Агенты сюда не ходят напрямую — только через `chronicle report submit` / `chronicle finish` (outbox).

| Ответ | Когда |
|---|---|
| `202 { ok, duplicate: false, segmentId, candidates, unknownEntries[] }` | принят; `unknownEntries` — ID из `usage`, которых нет в базе (пропущены) |
| `200 { ok, duplicate: true, segmentId, … }` | этот `(agent, session, seq)` уже принят — ничего не изменилось |
| `400 { error }` | тело не JSON |
| `422 { issues[] }` | не соответствует контракту; outbox клиента откладывает такой отчёт в `rejected/` |

**`GET /v1/facts?from=&to=&person=&project=`** (v2) — сырые факты за период: сессии, сегменты, ходы, активность, результаты, коммиты, файлы. Основа для `chronicle report day` и внешних отчётов.

### Знания

**`GET /v1/knowledge/search?q=&remote=&host=&path=&name=&limit=`** — нечёткий поиск по активным записям: общие + записи проекта, из которого ищут. Проект определяется по `remote`, иначе по `host + path`; записи чужих проектов не возвращаются. `limit` — по умолчанию 10. Каждое попадание увеличивает `found`.

```json
[{ "id": "bun-lockfile-old-server", "scope": "global", "kind": "trap", "title": "…", "score": 0.82 }]
```

`scope` — `global` или ID проекта.

**`GET /v1/knowledge/:id`** — запись целиком (`id`, `projectId`, `kind`, `title`, `symptoms`, `cause`, `fix`, `tags`, `status`, счётчики); увеличивает `opened`. `404`, если записи нет.

**`POST /v1/knowledge/:id/usage`** — тело `{ "helped": true | false | null }` → `204`; `404` — записи нет, `422` — тело не то.

**`POST /v1/import/entries`** — перенос уже отобранных записей из другой системы мимо курирования: `{ entries: [{ id, project | null, kind, title, symptoms, cause, fix, tags, note, stats? }] }` → `{ imported[], skipped[] }`. Идемпотентен по `id`, вся пачка — одна транзакция.

### Служебное

**`GET /v1/health`** → `{ "ok": true }`, без токена.

## 6. MCP

`POST /mcp` — Streamable HTTP, тот же bearer-токен. Только чтение и учёт пользы:

| Инструмент | Аргументы | Что делает |
|---|---|---|
| `knowledge_search` | `query`, `project_remote?`, `limit?` | как `GET /v1/knowledge/search`; проект — по remote |
| `knowledge_get` | `id` | запись целиком |
| `knowledge_used` | `id`, `helped` | отметка пользы |

Отчёты сессий через MCP не принимаются: у удалённого MCP нет outbox, при недоступном сервере отчёт потерялся бы. Подключение агентов — [install.md](install.md).

## 7. CLI `chronicle`

Клиент для людей и агентов. Настройки — `~/.config/chronicle/config.json` (`serverUrl`, `token`, `host`, `extractModel`), переменные `CHRONICLE_URL`, `CHRONICLE_TOKEN`, `CHRONICLE_HOST` важнее файла. Любая сетевая команда сначала пытается отправить накопленный outbox.

**Знания**

| Команда | Что делает |
|---|---|
| `chronicle search <текст ошибки> [--limit N]` | поиск; проект — по git текущего каталога |
| `chronicle show <id>` | запись целиком (markdown) |
| `chronicle used <id> --helped yes\|no\|unknown` | ручная отметка пользы |

**Отчёты**

| Команда | Что делает |
|---|---|
| `chronicle finish --agent <имя> (--session <id> \| --hook) [--detach]` | итог сессии: лог → выжимка → отчёт сегмента → outbox. `--hook` — ID сессии из JSON на stdin, `--detach` — в фоне |
| `chronicle replay --agent <имя> --session <id>` (v2) | пересборка сессии целиком (`replace`) |
| `chronicle report submit <файл\|->` | отправить готовый `SessionReport` (проверяется по контракту до постановки в очередь) |
| `chronicle report day [дата] [--person] [--project]` (v2) | отчёт за день: по проектам время `X ч (паралл. Y ч)`, эпизоды с результатами и коммитами, итог дня |
| `chronicle outbox [list\|flush]` | очередь неотправленных отчётов |

**Для интеграций** (без сети)

| Команда | Что делает |
|---|---|
| `chronicle schema` | JSON Schema выжимки — для `--json-schema` агентов |
| `chronicle last --agent <имя>` | последний итог `finish` агента (JSON) — для уведомлений |
| `chronicle statusline [--agent <имя>]` | строка статуса: последний итог и очередь |

Локальное состояние клиента — `~/.local/state/chronicle/`: `outbox/` (и `outbox/rejected/` с причинами отказа), `sessions/` (watermark и номер сегмента по сессиям), `finish.log`.
