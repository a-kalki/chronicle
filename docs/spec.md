# Спецификация chronicle

Сервис, независимый от агента: принимает итоги рабочих сессий от любых агентов (Claude Code, pi, agy) на любых машинах и отвечает на два главных вопроса о работе человека:

1. **Что сделано** — для команды это вклад, для заказчика — результат.
2. **Сколько работал** — для команды это вовлечённость, для заказчика — основание оплаты.

Остальные метрики (§4) вспомогательные: данные под них хранятся, считаются по потребности.

Отдельный контур — **знания**: ловушки окружения и инструментов, полезные в будущих сессиях.

## 1. Цели и не-цели

**Цели:**
- один источник правды для всех машин и всех агентов;
- **сохранять факты** так, чтобы любую отчётность можно было построить потом — в этом сервисе или во внешнем (у каждой команды может быть свой);
- время и результат привязаны к **проекту, в котором шла работа**, а не к каталогу запуска агента; работа в нескольких проектах за одну сессию не теряется;
- время проверяемо и воспроизводимо: отчёт вычисляется из сырых меток по явным правилам, смена правила — пересчёт, а не правка данных;
- явный версионированный контракт, по которому любой агент доставляет данные;
- качество базы знаний обеспечивает сервис, а не агент; польза знаний измеряется данными.

**Не-цели (пока):**
- развитая отчётность и аналитика — минимум (§5), остальное потом или во внешнем сервисе;
- разграничение доступа — все видят всё, нужен только токен;
- сущность Customer (заказчик) — только задел (§3);
- подсказка «на чём остановились» (`next_step_hint`).

## 2. Решения

| Решение | Почему |
|---|---|
| Центральный сервис на сервере, клиенты на всех машинах | Два контура, одни проекты, будущая команда; сервер доступен в 99% случаев |
| Локальная очередь (outbox) в клиенте | Оставшийся 1%: отчёт не теряется, уходит при появлении связи |
| Проект узнаётся по нормализованному git remote | Пути на ноутбуке и сервере разные, проект один |
| **Проект — у хода, а не у сессии** | Сессия, начатая в одном репо, часто работает в другом; привязка к `cwd` запуска теряет и время, и коммиты |
| **Ход (реплика человека + работа агента до следующей) — мельчайшая единица разметки** | Смена фокуса почти всегда начинается с реплики человека; у хода есть точное время |
| **Проект хода определяет адаптер по путям инструментов, фокус — модель при выжимке** | Проект проверяем детерминированно; смысловую границу «другая часть работы» по путям не найти |
| **Эпизод, время и метрики — проекции, не таблицы** | Правила (порог простоя, склейка эпизодов) можно менять задним числом |
| **Время человека — объединение интервалов по всем его сессиям** | Параллельные агенты не дают двойных часов; параллельность видна отдельно |
| Session и Segment — транспорт | Это артефакты агента, а не единицы работы человека |
| Агент присылает сырую выжимку, сервис курирует знания | Агенту минимум работы; правила качества в одном месте; курирование можно перезапустить |
| Кандидаты в знания неизменяемы, курированная база — производная | Можно пересобрать базу при смене правил |
| LLM для курирования — в сервисе, провайдер в настройках (по умолчанию `deepseek/deepseek-flash`) | Агент не обязан уметь сливать записи |
| База знаний сужена до ловушек и неочевидных фактов | По статистике pi-chronicle помогали только они; практики и архитектура — в документацию проекта |
| SQLite (`bun:sqlite`) | Без внешних зависимостей, удобно для аналитики |
| Valibot + `@valibot/to-json-schema` — единственные зависимости ядра | Как в u7-school; один источник для TS-типов, валидации и JSON Schema, которую требуют `--json-schema` агентов |
| Выжимку делает дешёвая модель агента | Работа простая (сжать сессию по промпту), дорогая модель не нужна |
| Отчёты доставляются только через локальный CLI-клиент | Только он гарантирует outbox; удалённый MCP при недоступном сервере данные потеряет |

## 3. Модель

```text
Справочники:  Person      Project ─< ProjectRemote      (Customer — задел)

Факты (хранятся, неизменны):
  Session ─< Segment ─< ActivityEvent   at, actor
                     ─< Turn            idx, at, project, focus
                     ─< Outcome         project, focus, text
                     ─< Commit          project, hash, subject, at
                     ─< SegmentFile     project, path
                     ─< KnowledgeCandidate → KnowledgeEntry (курирование)

Проекции (вычисляются при чтении):
  Episode · TimeEntry (человек × проект × день) · Metrics · Report
```

### Person
- `id` — slug (`nur`); токен клиента в настройках сервиса сопоставлен человеку;
- сессия получает `person` по токену, с которым пришёл отчёт. `host` остаётся атрибутом источника.

### Project
- `id` — slug (`u7-school`);
- `remotes[]` — нормализованные remote (`git@github.com:x/y.git` → `github.com/x/y`; SSH-алиас хоста раскрывается в настоящий хост);
- если remote нет — идентификация по `host + path`;
- проектом считается только git-репозиторий: пути вне git (`~/.pi/agent`, `/tmp`) проекта не образуют.

### Customer (задел)
Не вводится. Если понадобится — либо `customer` у проекта, либо отчётность целиком во внешнем сервисе поверх `GET /v1/facts`. Модель фактов от этого не меняется.

### Session и Segment (транспорт)
- **Session** — `(agent, agentSessionId)`: уникальна; хранит `person`, `host`, `cwd` и `launchProject` — проект каталога запуска (справочно, для метрики «работа вне проекта запуска»).
- **Segment** — единица приёма: один `/finish`. Продолженная сессия присылает следующий сегмент с дельтой. Ключ идемпотентности: `(agent, agentSessionId, seq)`. Повторная отправка того же сегмента ничего не меняет.
- `summary` сегмента — одна фраза о результате, для ленты.
- Сегмент может быть помечен `superseded` — его факты работы заменены пересборкой сессии (§4 «Пересборка»); кандидаты знаний остаются.

### ActivityEvent
- `{ at, actor: 'user' | 'agent' }` внутри сегмента.
- `activitySource` сегмента: `log` (точные метки из лога) или `coarse` (известен только интервал).

### Turn (ход)
- `idx` — номер хода в сессии (сквозной по сегментам), `at` — время реплики человека.
- Ход длится от своей реплики до реплики следующего хода (или конца сегмента); события активности относятся к ходу по времени.
- `project` — определяет адаптер по путям в вызовах инструментов хода: путь → git-корень → проект. Веса: правка файла (Edit/Write) — 3, `cd`/git-команда в shell — 2, чтение и поиск — 1; побеждает наибольший вес. Ход без путей наследует проект предыдущего, первый ход — `launchProject`. Если проекта нет ни у одного хода и запуск вне git — `project = null`.
- `focus` — короткая метка части работы (≤ 60 символов, свободный текст) от модели при выжимке: модель размечает эпизоды диапазонами номеров ходов (см. `agent-contract.md`). Для устойчивости меток в промпт подаются недавние фокусы затронутых проектов с просьбой переиспользовать подходящие.
- Сегмент без ходов (старые данные, `coarse`) читается как один ход: весь интервал → проект сессии, фокус пуст.

### Outcome (что сделано)
- `{ project, focus, text }` — конкретный результат эпизода: что реализовано, исправлено, решено. Язык результата, а не действий.
- Доказательства — коммиты и файлы того же проекта за интервал эпизода.

### Commit и SegmentFile
- Коммиты автора (по `user.email` каждого репо) **из всех репозиториев, затронутых ходами сегмента**, за интервал сегмента: `{ project, hash, subject, at }`. Один коммит, пришедший из двух параллельных сессий, в проекциях учитывается один раз (`project + hash`).
- Изменённые файлы — пути относительно корня своего репо, с проектом.

### Episode (проекция)
- Подряд идущие ходы человека с одинаковыми `(project, focus)` — **по всем его сессиям**, в порядке времени.
- Пауза больше порога простоя внутри эпизода — простой (не входит в активное время), но не граница.
- Возврат к тому же фокусу после другого — новый эпизод (это «возврат», §4).
- Эпизод не переходит границу дня (локальная дата человека).

### Время (проекция)
- **Активные интервалы** сегмента: промежутки между соседними событиями не длиннее `idleGapMinutes`; для `coarse` — весь интервал. Порог — параметр чтения.
- Интервал относится к проекту хода, в котором лежит.
- **Время человека** за период = длина объединения всех его активных интервалов по всем сессиям.
- **Время по проекту** = длина объединения интервалов этого проекта.
- **Параллельное время** = длина участков, где одновременно активны две и более сессии. Показывается как есть: `5.6 ч (паралл. 1.1 ч)`; сумма по проектам может превышать время человека ровно на параллельные участки разных проектов.
- `actor` событий сохраняется: время агента без участия человека можно выделить позже, не меняя данные.

### KnowledgeCandidate (вход, неизменяемый)
- `scope`: `project` | `global`;
- `kind`: `trap` (ловушка: симптом → причина → решение) | `fact` (неочевидный факт окружения: пути, серверы, ограничения);
- `title`, `symptoms[]` (дословные тексты ошибок — главный ключ поиска), `cause`, `fix`, `tags[]`;
- статус курирования: `pending` → `created` | `merged` | `discarded` + причина решения.

### KnowledgeEntry (курированная запись)
- `id`, `scope` (`global` или `project:<id>`), `kind`, `title`, `symptoms[]`, `cause`, `fix`, `tags[]`;
- `history[]` — `{ at, candidateId, action, note }`;
- `status`: `active` | `archived`;
- статистика: `found` (сколько раз попала в выдачу), `opened`, `helped`, `notHelped`, `lastUsedAt`.

### Usage
- `{ entryId, sessionId, helped: true | false | null }` — приходит в отчёте сегмента или отдельным вызовом.

## 4. Метрики (вспомогательные)

Все считаются из фактов §3; хранить отдельно ничего не нужно. Реализуются по потребности.

**Организованность**
- проектов на сессию (норма — 1); доля времени вне `launchProject`;
- сессии длиннее рабочего дня;
- переключения фокуса за день, средняя длина эпизода, возвраты к тому же фокусу;
- параллельность: сколько сессий и проектов активны одновременно.

**Вовлечённость**
- активные дни, начало и конец рабочего дня, регулярность;
- самый длинный непрерывный эпизод;
- доля простоя внутри эпизодов.

**Результативность**
- результаты (Outcome) и коммиты на активный час;
- доля «пустых» сессий: время есть, результата нет;
- время от начала до готовности задачи (когда появятся задачи).

**Работа с агентами**
- соотношение времени человека и агентов, автономное время агента;
- токены и деньги по проектам (потребует поля в контракте);
- распределение по агентам и моделям.

**Качество и потери**
- повторные попадания в ту же ловушку;
- время эпизодов, ушедшее на ошибки (эпизоды с `chronicle search`);
- откаты и доля коммитов `fix`.

## 5. Процессы

### Приём отчёта (синхронно)
Валидация по контракту → запись сегмента, активности, ходов, результатов, коммитов, файлов, кандидатов и usage в одной транзакции → ответ `202` с ID. Неизвестные проекты (по remote) создаются. Курирование не блокирует приём.

Принимаются контракты v1 (накопленный outbox; читается как сегмент без ходов) и v2.

### Пересборка сессии
`chronicle replay --agent <a> --session <id>`: адаптер перечитывает лог сессии целиком (watermark с нуля), выжимка — без знаний (`knowledge: []`, `usage: []`, чтобы не плодить дубли кандидатов), отчёт уходит с флагом `replace`. Сервис в одной транзакции помечает прежние сегменты сессии `superseded` (их ходы, результаты, коммиты, файлы и активность из проекций исключаются; кандидаты знаний остаются) и пишет новый сегмент. Используется при смене модели разметки и для исправления ошибок.

### Курирование знаний (асинхронно, в сервисе)
Для каждого кандидата `pending`:
1. нечёткий поиск топ-5 похожих записей в своём scope и в общем;
2. LLM решает: `create`, `merge <id>` (с обновлёнными полями) или `discard` (тривиально, общеизвестно или полный дубль);
3. решение применяется и логируется в `history` записи и в кандидате.

Курирование можно перезапустить по всем кандидатам (пересборка базы).

### Архивирование
Записи без использования дольше `archiveAfterDays` переводятся в `archived`. Из поиска они исключаются, но не удаляются.

## 6. Интерфейсы

Все входы — тонкие адаптеры над одними use cases.

### HTTP API (`/v1`, JSON, `Authorization: Bearer <token>`)
- `POST /v1/reports` — приём сегмента (`SessionReport` v1 или v2);
- `GET /v1/facts?from=&to=&person=&project=` — сырые факты за период (сессии, сегменты, ходы, активность, результаты, коммиты, файлы) для отчётов здесь и во внешних сервисах;
- `GET /v1/knowledge/search?q=&project=&limit=` — нечёткий поиск по активным записям (project + global);
- `GET /v1/knowledge/:id` — запись целиком (увеличивает `opened`);
- `POST /v1/knowledge/:id/usage` — `{ sessionId?, helped }`;
- `GET /v1/health`.

### CLI `chronicle` (TS, основной путь для агентов)
- `chronicle search "<текст ошибки>"`, `chronicle show <id>`, `chronicle used <id> --helped yes|no`;
- `chronicle report submit <file|->` — отправка сегмента (через outbox);
- `chronicle outbox [list|flush]`;
- `chronicle finish --agent <name> --session <id>` — общая часть `/finish` для адаптеров;
- `chronicle replay --agent <name> --session <id>` — пересборка сессии;
- `chronicle report day [дата] [--person] [--project]` — минимальный отчёт: по проектам время `X ч (паралл. Y ч)`, эпизоды с результатами и коммитами; итог дня.

При каждом вызове CLI сначала пытается отправить накопленный outbox.

### MCP (`POST /mcp`, Streamable HTTP, тот же bearer-токен)
Только чтение и учёт пользы: `knowledge_search`, `knowledge_get`, `knowledge_used`. Отчёты сессий через MCP не принимаются — только через CLI с outbox (потеря `usage` при недоступном сервере допустима, потеря отчёта — нет).

## 7. Настройки

**Сервис** (`chronicle.server.json` + переменные окружения):
- `dbPath`;
- `tokens[]` — `{ token, person }`;
- `llm.model` — по умолчанию `deepseek/deepseek-flash`; `llm.apiKeyEnv` — по умолчанию `DEEPSEEK_API_KEY`;
- `idleGapMinutes` — по умолчанию 30;
- `timezone` — для границы дня в проекциях, по умолчанию `Asia/Oral`;
- `archiveAfterDays` — по умолчанию 120.

**Клиент** (`~/.config/chronicle/config.json`): `serverUrl`, `token`, `host` (`laptop`, `kalki-server`), `outboxDir`.

## 8. Хранилище (SQLite)

Таблицы: `persons`, `projects`, `project_remotes`, `project_paths`, `sessions` (`person`, `launch_project`), `segments` (`superseded`), `activity_events`, `turns`, `outcomes`, `commits` (`project_id`), `segment_files` (`project_id`), `knowledge_candidates`, `knowledge_entries`, `knowledge_history`, `knowledge_usage`, `schema_migrations`.

Схема версионируется миграциями; переход на v2 — миграцией без конвертации старых данных (старые сегменты читаются по правилу «сегмент без ходов», живые сессии пересобираются через `replay`). Перед миграцией на сервере — копия файла БД. Бэкап — файл БД (`sqlite3 .backup`) по расписанию на сервере.

## 9. Миграция из pi-chronicle (выполнена 2026-10-17)

- Перенесены 30 из 53 записей — только ловушки и факты, отбор LLM с ручной проверкой; исходные ID и статистика «помогло» сохранены (история записи — `imported`). Практики и решения не переносились.
- 54 сессии worklog → сегменты 1 с `coarse`-активностью (интервал = начало + активные минуты).

## 10. Структура кода

```text
chronicle/
  src/domain/      # сущности, правила (активное время и интервалы, проект хода, нормализация remote, схожесть)
  src/app/         # use cases: submitReport, replay, facts, report, curate, search, recordUsage, archive
  src/infra/       # sqlite-репозитории, миграции, LLM-клиенты
  src/http/        # Bun.serve, MCP
  src/cli/         # клиент chronicle + outbox
  contract/        # valibot-схемы v1 и v2: SessionReport, ExtractResult; генерация JSON Schema
  prompts/         # общий промпт выжимки для всех агентов
  src/adapters/    # адаптеры агентов (claude-code, pi): активность, ходы, пути, выжимка
  src/finish/      # общая часть /finish и replay: состояние сессий, коммиты, сборка отчёта
  integrations/    # подключение к агентам: хук Claude Code, pi-пакет, скил recall
  docs/            # spec.md, agent-contract.md, plan.md
```
